## 0. 最高优先级约束：不得替用户启动 AA

后续任何模型、脚本和自动化工具都不得擅自启动、重启或操作 `AzureArchive.exe`。已知游戏路径、用户曾经测试过、刚完成构建、需要部署、需要验证，都不构成启动授权。

在用户没有明确说“AA 已经由我启动，并允许进行这次具体测试”之前，只能做以下工作：

- 编译源码、生成包、校验 DLL 哈希；

- 离线读取 AAP、AAP2、AAS、BepInEx 日志和 Rukari 诊断日志；

- 阅读和修改源码、测试代码、文档。

不得使用 `Start-Process`、启动器、计算机操作工具或隐式 helper 启动游戏。不得点击游戏窗口、切换工程、保存/发布或播放项目。

如果模型误启动了 AA，必须立即停止后续 UI 工作，明确报告事故，确认没有 `AzureArchive` 进程残留，再等待用户决定下一步。不能把启动隐藏在“部署”“探针”或“检查环境”中。

## 2. 本次要解决的实际问题

目标是让“表面为空、附加指令不为空”的对白行沿用 AA 官方的保存、编译、播放链路。

典型输入：

```text
可见对白文本：空
additionalPrompt：#aavt;char;3;reset;duration=600;easing=easeInOut
```

历史问题是：AAP 预览可以执行附加指令，但正式播放的官方 AAS 编译结果只出现普通的官方脚本，例如：

```text
#3;h
#3;order;1
```

AA 因此可能把这一行当作没有需要等待的内容，在 AUTO 或连续推进时直接跨过，导致 AAVT 只在编辑器预览生效、正式播放不生效。

## 3. 当前实现的改动

### 3.1 官方编译结果边界上的 1 ms 锚点

文件：

```text
src/AzureArchive.VideoTools/Runtime/EditorEmbeddedDirectivePatch.cs
src/AzureArchive.VideoTools/Interop/OfficialCompilationMappingCapture.cs
```

当同时满足以下条件时，补入官方可识别的时间性指令：

- 可见对白文本为空；
- `additionalPrompt` 中存在已注册的 `#aavt` 或语音指令；
- 指令解析无错误；
- 清理后的官方文本仍为空；
- 原编译结果中没有官方 `#wait;`。

锚点是：

```text
#wait;1
```

锚点只附加在托管的 `ScriptKr` / 官方编译结果上，不修改作者在 AAP 中看到的对白文本，也不把 `#aavt` 交给官方指令解析器。这样做的目的只是让官方 AAS 产生一个有时间轴的行，并保留原有的额外指令映射。

当前有两个 ScriptKr postfix：

- `OfficialCompilationMappingCapture.ScriptKrPostfix`，优先级较高，负责编译映射观察；
- `EditorEmbeddedDirectivePatch.AnchorOfficialScriptPostfix`，优先级靠后，负责兜底。

两者都先检查已有 `#wait;`，所以正常情况下不会重复追加。后续模型修改时必须保留这个幂等条件；不要再新增第三个锚点 hook。

### 3.2 正式播放的精确行回退

文件：

```text
src/AzureArchive.VideoTools.Core/Commands/CommandTimelineContracts.cs
src/AzureArchive.VideoTools.Core/Commands/PlaybackCommandBinding.cs
src/AzureArchive.VideoTools.Core/Commands/PlaybackAdvanceDispatchPolicy.cs
src/AzureArchive.VideoTools/Runtime/PlayerCommandObservationRuntime.cs
```

当正式播放确实产生了 AA 的 Advance 窗口，但身份映射无法唯一判断时，命令批次可以按“实际播放行号”精确回退。空正式行只允许 exact-row 匹配，不允许借用相邻行或模糊身份。这是安全兜底，不是锚点的替代品：如果 AA 根本没有产生 Advance 窗口，运行时回退没有机会执行。

## 5. 严格的后续测试条件

后续模型只能把下面这段原样发给用户，等待用户自己操作：

得到用户明确授权后，才可以进行以下测试。授权必须针对当前这次测试，不能用很久以前的“开始部署”或“已打开”代替。

### 5.3 正式播放测试

用户重新启动 AA 后，才可以进行下列测试：

1. 从工程开头手动推进到第一条命令行。
2. 确认三号槽位执行 `reset`，持续时间为 600 ms。
3. 推进到第二条命令行，确认人物位置和镜头动作执行，且第二条从上一条实际状态继承。
4. 从头重播，直接开启 AUTO，确认两条命令行都执行。
5. 关闭 AUTO，手动推进一次，再切回 AUTO，确认后续命令仍执行。
6. 在同一行连续点击绿色预览，确认槽位不跳回一号，且起点不重复叠加。
7. 观察正式播放诊断日志；每个命令行应有 `CommandBatch`、`QUEUE_SCENE_COMMANDS`、`SCENE_DISPATCH_AUTHORIZED` 和 `SCENE_COMMAND_DISPATCHED`，不应只出现 `OrdinaryRecord`。

## 7. 现象到原因的快速判断

| 现象 | 优先检查 |
| --- | --- |
| 预览有效，正式播放无效 | 保存后 AAS 是否含 `#wait;1`；AAP/AAS 是否同名同版本；正式播放是否读取了当前存储根 |
| 手动有效，AUTO 无效 | 官方编译结果没有时间性行，或新 AAS 尚未由新 DLL 发布 |
| 所有带 AAVT 的行都没有 `SCENE_COMMAND_DISPATCHED` | 当前播放没有找到有效 AAP/AAS 对，或插件未注册/未加载 |
| 出现 `AmbiguousIdentity` | 重复脚本身份或映射证据不唯一；不要用邻行猜测替代 |
| 出现 `EMPTY_FORMAL_ROW_FALLBACK` | AA 已给出正式行，但身份映射无法唯一确认；检查 exact-row、项目版本和 AAS 哈希 |
| 出现 `Assembly AzureArchive.VideoTools.Core.dll is not registered in il2cpp` | 运行时类型注册/游戏 BepInEx 互操作环境问题；先收集完整启动日志，不能仅凭这一行判断 AAVT 指令错误 |
| AAP 更新而 AAS 未更新 | 用户只保存了草稿，未完成官方编译/发布；不要把该工程用于正式播放验收 |

## 8. 交接时不可做的事

- 不得再次自动启动 AA 以“确认一下”。
- 不得把旧 AAS 没有 `#wait;1` 当成新代码失败。
- 不得直接写入或手工改造 AAP/AAS 伪造正式发布结果。
- 不得把 AAP 预览成功当成 AAS 正式播放成功。
- 不得在映射不唯一时用相邻对白、脚本文本相似度或猜测槽位兜底。
- 不得为了测试关闭用户已经运行的 AA；只检查进程状态。若模型自己误启动，才按第 0 节的事故处理执行。

## 9. 完成标准

只有同时满足以下条件，才能声称“空对白正式播放修复完成”：

1. 用户在 AA 1.01 中用新 DLL 自己启动并完成一次官方保存/编译/发布；
2. 保存后的 AAS 对应命令行含官方 `#wait;` 时间性脚本；
3. 用户确认手动正式播放执行；
4. 用户确认直接 AUTO 从第一条开始也执行；
5. 用户确认手动切 AUTO 后仍执行；
6. 诊断日志出现每条命令行的正式分发记录，没有依赖模糊身份猜测；
7. 离线探针和 AAS 读取结果已保存为交接附件。

在这些条件完成前，结论只能写成“已完成编译和离线检查，等待用户授权后的正式播放验收”。
