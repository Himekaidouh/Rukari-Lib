# 镜头窗口与层写入（2026-10-13）

> **同日改版（用户反馈后）**：镜头层编辑器**已从独立窗口搬进「更多的画面效果」的镜头模式**，独立窗口与其源码已删除。本文 §2 描述的窗口行为与 §5 的部署哈希属于改版前的记录；**当前实现见 §7**。层写入 API（§3）、`CameraLayerStack`、以及"镜头层只能有一个写者"的结论都没有变。

## 1. 目的与范围

叠加式效果模型（[docs/44](44_叠加式效果模型_20261013.md) §6）的第一扇窗口：**镜头效果**。它拥有 `camera` 与 `camera:background` 两层，层内**顺序即时间**，一次事务写回两层，且只写自己的资源。

用户已拍板的四件事（`docs/44` §6 表格）：删掉时间轴与关键帧、层内自动顺序累加、首个改造对象是镜头层、`PresentationTimeline*` 删除。

**不属于本轮**：其它层的窗口（预设效果窗口仍是"一次一条指令"的草稿模式）、层内逐段参数编辑（改一段 = 删掉再加一段）、跨层优先级（"覆盖别的窗口的层"）。

## 2. 窗口行为（可执行契约）

| 方面 | 规则 | 依据 |
|---|---|---|
| 内容 | 固定两个层区：`camera`（镜头）、`camera:background`（背景镜头）。每区一行一个效果，**行号即播放顺序** | `CameraLayers.All` |
| 行文本 | `序号. 设置 x=0 y=0 缩放=1.2 · 300ms · 渐慢`；带 `at=`/`interrupt=` 的手写段会照实显示，不会被悄悄重排成"没有时间" | `CameraLayerLabel.Of(canonical)` |
| 层表头 | `镜头 · 本层 2 段 · 共 0.70 s`，与预设窗口同一套 `EffectLayerSummary`（本层自己的长度，不是轨上完成时刻） | `EffectLayerSummary.FromDirectives` |
| ＋ 加一段 | 取**画面编辑器当前正在发布的镜头草稿**，按草稿自己的 scope 落进对应层，追加到该层末尾。没有草稿时说明要先在「更多的画面效果」里调镜头 | `ICameraLayerSource.Draft()` |
| 上移 / 下移 / 删除 | 只在本层内移动或删除；三者在**应用之前不动台词** | `CameraLayerPanel.Move/Delete` |
| 应用 | 把**两层一起**写进当前句（一次共享事务）。空层写成 0 条 = 删掉该层的行 | `CameraLayerEdit` |
| 刷新 | 丢弃未应用的改动并强制重读；**未应用时不会自动重读**（4 Hz 自动重读在有草稿时停用），避免把用户正在叠的草稿冲掉 | `Poll` |
| 撤销 | 走共享事务的撤销（与其它页面同一条撤销链） | `ICameraLayerSource.Undo()` |
| 尺寸 | 高度跟随行数；**内容装不下时少画行**，表头写"另有 N 段放不下"，状态行永远钉在手头矩形底部 | `Capacity` + `Draw` |
| 日志 | 状态行一变就写一行 `[camera-layer] … · 待应用=是/否` | `LogStateOnce` |

关于尺寸那条：宿主给页面的是**上一帧**页面请求的高度，所以刚加完一段的那一帧矩形可能还差一行。窗口不会画到矩形外面（宿主只能命中矩形内的区域），下一帧高度跟上后行自然补齐。

## 3. 写入路径

### 3.1 为什么不用 `EditorCommandDocumentService`

那个服务的读与回读都经过 `EditorCommandDocumentComposer.Read`，而它**按设计拒绝**"同一资源两条指令"的行——正是本窗口要产生的行。`WriteExact` 本身不依赖 1:1（它最终也是调共享事务的 `Replace`），所以本窗口直接走 `IEditorDocumentService`：**token + revision 双重核对**不变，回读改用**提取器**（与播放同一条读取路径）。

### 3.2 层写入 API（Core，纯逻辑）

```
Result<EditorCommandLayerEdit> PreviewReplaceResource(
    string sourceText, string expectedRevisionSha256, string resourceKey,
    IReadOnlyList<string> directives, bool acceptLegacyCharAlias = true)
```

语义与保证（`EditorCommandLayerReplaceTests` 9 项）：

- 该资源的**所有行**被替换成给定顺序的若干条；**0 条 = 删除该层**；层的第一行留在原位（层不会跑到文件末尾）。
- 每条草稿必须是**恰好一条**受支持的资源行，且**必须属于 `resourceKey`**——一个窗口不能把效果写进别人的层。
- 文档本身有无法解析的行 → 整体拒绝（不做逐行手术）。
- 其余每一行**逐字保留**（含行尾与缩进）：结果会重新提取，并把**其它层的行逐条比对**，任何丢失或重排都返回失败而不返回文本。
- revision 必须匹配，否则拒绝（共享事务那一层还有一次同样的核对）。

### 3.3 游戏侧

`CameraLayerApiSource`（MoreEffects）：
读 → `IEditorDocumentService.ReadSelection()` → `CameraLayerRead.From(原文…)`；
草稿 → `VisualEditorBehaviour.CurrentCameraDirective`（画面编辑器当前发布的规范化指令）→ 提取器定层 → 公文化；
写 → 两层依次 `PreviewReplaceResource` 链到同一份文本 → 归属冲突检查（`AavtDirectiveOwnershipPolicy`）→ 一次 `Replace` → 回读校验 revision → 再用提取器读回给窗口。

## 4. 已知后果与下一步（需要用户决定）

**画面编辑器的镜头组现在是 `camera` 层的第二个写者**：它按 1:1 编辑"这一条指令"，所以当本窗口把某一层写成 **2 段以上**后，画面编辑器对那一句的读取会失败（`declares more than one directive for public slot 0`），整页都读不了这一行。窗口在写入后的状态行会直说这件事，并指出后续镜头改动应在这一页做。

三个选择：

| 选项 | 含义 | 代价 |
|---|---|---|
| A. 画面编辑器**交出镜头组**（推荐） | 镜头层唯一写者 = 镜头窗口；画面编辑器只保留人物与屏幕文字 | 画面编辑器要删掉/隐藏镜头控件；用户调镜头改到镜头窗口（或先在编辑器里拖动、再用草稿加入） |
| B. 画面编辑器只改**第一段** | 读取回退到提取器 + "取每资源第一条" | 会静默丢弃第一段之后的段，**不建议** |
| C. 保持现状 | 谁先写谁说了算，冲突用报错暴露 | 两句工具互相锁死同一行，用户要手工删段 |

在 A 落地之前，建议的用法是：**镜头只在一个地方写**——要么一直在画面编辑器里编辑（1 段），要么把它交给镜头窗口（多段）。

### 4.1 决定：A（用户 2026-10-13 拍板），下一轮执行

**"交出镜头组"的确切含义**：镜头**模式仍然存在，但它只负责"做出草稿"，不再负责"写进台词"**。用户在编辑器里拖动镜头框、调时长与缓动，草稿照旧发布（`VisualEditorBehaviour.CurrentCameraDirective`），然后到镜头窗口按「＋ 加一段」把它叠进那一层。

落地要点（`src/Rukari.MoreEffects/Runtime/VisualEditorBehaviour.cs`）：

1. `ApplyDraft` 的 `_mode == VisualEditorMode.Camera` 分支去掉写入（当前它经 `ApplyUpsertSelectedOnMainThread` 写一条指令）——这是 1:1 写者。
2. `ApplyDraft`/`UpdateButtons` 里镜头模式的"应用草稿"按钮改为不可用，并把它旁边的文案改成"镜头由「镜头效果」窗口写入"；`_operationMessage` 同理。
3. `VerifyDraftAgainstSelected` 在镜头模式下**不再调用** `PreviewUpsertSelectedOnMainThread`：那是一次 1:1 预览，在"一层两段"的行上必然失败，会把编辑器页显示成"草稿已过期"。
4. 保留：镜头框拖动、scope 选择（整体/仅背景）、时长与缓动循环、`PublishCameraDraft`、`ClearCameraDraft`、只读镜头读取（帧与读数）。
5. 人物与屏幕文字两组的读写**完全不动**（它们各自 1:1，仍然自洽）。
6. 需要新文案的位置：模式按钮、应用按钮、操作消息、以及"没有草稿"时的提示（当前 `CameraLayerApiSource.Draft()` 已经会提示先去编辑器调镜头，两边要一致）。

测试与验证：这一段是 Unity 侧代码，没有离线测试可钉；验收靠实机——(a) 镜头模式下没有可用的"应用草稿"；(b) 拖动镜头后镜头窗口的「＋」能拿到草稿；(c) 一层两段的行打开编辑器页不再出现 `declares more than one directive`；(d) 人物与屏幕文字的"应用草稿"照旧可用。

## 7. 改版：镜头层编辑器搬进画面编辑器（用户反馈后，同日）

用户反馈原话："为啥不把这个按钮集成到更多的画面效果里面呢，只是两个按钮而已，为啥要额外添加窗口啊"。
结论：**这个判断是对的**。窗口能力是为"必须同屏"的页面做的（时间轴要贴在编辑器旁边看）；镜头层的编辑不需要同屏——它本来就是"在同一个页面里继续下一步"。于是独立窗口、`CameraLayerApiSource`、`ICameraLayerSource` 与窗口面板（含 12 项面板测试）**全部删除**。

### 7.1 现在的形状

镜头模式（`VisualEditorBehaviour.CameraLayer.cs`，partial 文件）新增：

| 控件 | 位置 | 作用 |
|---|---|---|
| 段号行 `1..6` | 角色模式"旋转预设"那一行（镜头模式本来空着） | 点一下选中该层第 N 段；不存在的段置灰；高亮＝当前选中 |
| `＋ 加为下一段` | 角色模式旋转盘右侧那条空档 | 把当前镜头草稿按它自己的 scope 追加到该层末尾，并把 scope 切过去 |
| `上移` / `下移` | 同上 | 只在本层内移动选中的段 |
| `删除第 N 段` | 同上 | 删除选中的段 |
| 信息行第 3 行 | 现有 inspector | `整体：本层 2 段 · 共 0.70 s　选中 2. 设置 缩放=1.6 · 400ms · 匀速` |
| 应用按钮 | 现有按钮 | **镜头模式下它写的是"我这一层"**，标签变成 `应用镜头层`（有改动时 `应用镜头层 *`） |

### 7.2 为了让它成立而做的三处非界面改动

1. **多段行可以被读了**：`EditorCommandDocumentComposer.ReadAllowingMultipleResources`（提取器口径），`EditorCommandDocumentService.ReadSelection` 改用它——否则一层两段的行会让**整页**读不出来（`declares more than one directive for public slot 0`）。
2. **一次一条指令的写者只对自己那条资源负责**：`PreviewUpsert` 只在"它要写的那条资源已有 2 条以上"时拒绝，并明说"请在负责这一层的窗口里修改"；写别的资源不再被别人的多段挡住。`Read`（严格版）保持不变，仍是那条规则的公开入口。
3. **镜头模式不再做 1:1 预览**：`SetCameraDraft` / `SelectCameraScope` / `PublishDraftResult` 里的 `PreviewUpsertSelectedOnMainThread` 全部不走，改为显示"按「＋ 加为下一段」加入哪一层"。

### 7.4 实机验收点

1. 镜头模式里应看到：段号行 `1 2 3 4 5 6`（没有的段是灰的）、`＋ 加为下一段`、`上移`、`下移`、`删除这段`。
2. 拖动镜头框后 `＋ 加为下一段` 可用；点它 → 信息行出现 `本层 1 段 · 共 X.XX s　选中 1. …`，段号 `1` 高亮。
3. 再拖一次、再加 → `本层 2 段`；`上移`/`下移`/`删除` 只动本层。
4. 按 `应用镜头层` → 写入当前句；状态与草稿区显示结果；若这一层 ≥2 段，会提示"一次一条指令的编辑器不再适合改这一层"。
5. 播放这一句：两段按顺序播放（同一 screen track 追加）。
6. **回归**：人物模式与屏幕文字模式的"应用草稿"照旧可用（它们是 1:1，不受影响）；切到镜头模式时不应再看到 `草稿已过期 / 来源不同步`。

### 7.5 实机发现的缺陷：草稿形式搞错了（同日修复）

第一次实机里 `＋ 加为下一段` 全部报 **`当前镜头草稿无法写入台词：InvalidOperationException`**。

原因：画面编辑器发布的是**公开形式**（`#aavt;camera;set;…`，见 `VisualCameraDraftBuilder` 第 95–99 行），而我的入口 `CameraDraft.FromCanonical` 只接受**规范化形式**（`#camera;set;…`），于是 `ToPublicDirective` 抛"Unsupported canonical AAVT resource family"。我的单元测试恰好喂的是规范形式，所以离线全绿、实机全红——**测试用错了形式**。

修复：入口改名 `CameraDraft.FromDirective`，**两种形式都接受**（先按文档形式交给提取器，失败再把规范化形式转换成公开形式），并补上以真实会话里那条 `#aavt;camera;set;x=270;y=0;zoom=1.364;duration=500;easing=easeOut` 为输入的回归测试（`CameraLayerStackTests.ADraftComesFromTheCameraDirectiveWhicheverFormItArrivesIn`）。

### 7.6 控件形状重做（同日第二次反馈）

用户反馈："首先按钮太小，其次，我是打算用下拉框选段数，按钮应该和底下的大按钮平级才对"。

改法：

- **去掉那一行 6 个小数字按钮**（28px，塞在角色模式旋转预设的空档里）。
- **段选择做成一个值按钮** `镜头段 2/3`：点一下切到下一段。**这一页没有弹出式控件**——时长、缓动、对齐、显示方式全都是"显示当前值、点一下换下一个"，所以"下拉框"在这里就是这个形状。若确实要弹出列表，需要新增一个弹出控件（可以再做）。
- **5 个控件放进两行标准大按钮**（42px 高、50px 行距，与整页一致）：第一行 3 列 `镜头段 2/3` / `上移` / `下移`；第二行 2 列 `＋ 加为下一段` / `删除第 N 段`。位置在镜头自己的 `复位`/`清空` 行下面，**`连续对话` 行随之下移 100px**（`LayoutCameraLayerControls` 返回该行 Y，相机模式下交给 `continueRowY`），草稿区高度由它派生，因此不会重叠。
- 空间是从游戏日志里量出来的，不是推算的：`[host] content=154,45 623x1356px; story=178,52 720x1567; scale=0.865`——镜头模式下 `复位/清空` 行之下到草稿区之间本来就有整片空档。

### 7.7 ＋ 加为下一段 提升为大按钮（同日第三次反馈）

用户反馈："非常，非常不明显，用户很难意识，而且它是必须点的，它应该和应用镜头层/撤销平级，用类似的按钮形式与按钮大小"。

改法：

- `＋ 加为下一段` **不再是一行控件里的一个**，而是底排第三个大按钮：与 `应用镜头层`、`撤销` **同一排、同一高度（64px）、同一种主题绘制**（`ToolTheme.ApplyButton(..., decorated: true, primary: true)`，与 `应用镜头层` 同为主按钮），有自己的 `RectTransform` / `Image` / `Text` / 命中矩形，点击走和其它两个大按钮同一条指针分支。镜头模式下这一排三等分，另两个模式仍是两等分。
- 它下面那两行 42px 现在只剩真正的次要控件：第一行 `镜头段 2/3` / `上移` / `下移`，第二行 `删除第 N 段`（整宽）。`连续对话` 仍随之下移。
- 没有草稿时它和其它两个按钮一样是禁用外观，信息行同时写着"调好镜头后按「＋ 加为下一段」"，所以"为什么是灰的"在屏幕上就有答案。

### 7.8 三段镜头"没有生效"：预览租约的相机预算按条数计（同日修复）

用户报告：一行里用了三段 `#aavt;camera;set;…`，"没有生效"，而且"点击后人物会抽搐一下回到原位然后再回去"。日志（`player-command-observation-20261013-184058.log`）里每一次预览都是：

```
observation sequence=…; status=EDITOR_PREVIEW_LEASE_REJECTED;
reason=Editor preview lease allows at most five character slots, five transient presets,
       10 spine overlay tracks and two independent camera scope resources.
```

根因在 `EditorPreviewLeasePlanner`：相机预算 `cameraResourceCount > 2` 是**按指令条数**累加的（`cameraResourceCount++`），写法来自"一个 scope 一条指令"的时代。所以**一行里超过 2 条镜头指令就直接被拒**，预览永远不会调度，每次被拒还会把场景回滚一次——这就是"抽搐一下回到原位再回去"。同一行里 `embedded-directive-capture … commands=3` 说明写入本身是成功的（三段都在文档里），坏的只是预览这一层。

修法：这个预算的语义是**资源**（报错文案自己写的是"two independent camera scope resources"），改成数**不同的相机资源**（`HashSet<EditorPreviewResourceKey>`，最多 `camera` 与 `camera:background` 两个）。其它三类（角色槽/预设/轨道）**保持按条数**不变——它们的楼层编辑器还不存在，等它们有层了再按同样的理由改。整行的场景预算（`MaxCommandsPerScene = 22`）不变，仍然是条数上限。

回归测试 `EditorPreviewLeaseTests.TheCameraBudgetCountsScopesAndNotSegments`：用真实会话里那三段原文 → 全部被租约接受、保持作者顺序、**footprint 只有 1 条**（同 scope 三段是一个资源）；两个 scope 各两段 → 2 条；`MaxCommandsPerScene + 1` 条 → 仍被场景预算拒绝。

部署：`AzureArchive.VideoTools.Core.dll` `2FC6352F1521E82D` → `9BFCE62A23F75B52`（MoreEffects 未变）；备份 `artifacts/deploy-backups/AA1.01-camera-lease-budget-20261013-185749/`。

## 8. 预设层成为层栈（同日，第二部分）

镜头那条路走通之后，同一套机械被泛化并接到了第二个家族：**`preset:{slot}`**。

### 8.1 先泛化（提交 `46c46a9`）

`CameraLayerSegment/Read/Edit/Apply/Stack` → `EffectLayer*`：它们本来就和镜头无关，只是"**一个窗口拥有的那些层，按它的显示顺序**"。栈由拥有它的窗口构造（镜头传两层，预设传一层），读也按传入的层集合过滤。

- **"这一层归谁"由栈判断**：`EffectLayerStack.Add` 拒绝不属于自己的层，并同时说出两边（"这个窗口负责的是镜头、背景镜头，加不了角色 3"）。草稿本身接受任何本版本认识的家族——这样判断只发生在一个地方。
- 行标签按家族分派（`EffectDirectiveLabel`）：镜头用自己的措辞，预设用预设编辑器自己的词汇（`压扁 幅度=0.15 频率=4Hz 循环=3 · 向右`），本版本不认识的家族**原样显示指令**。
- 顺手修掉一个真 bug：`LayerOf` 原本在找不到层时静默回落到镜头层（会把别人的效果记进镜头层），现在有显式归属检查。

### 8.2 预设窗口（本轮）

| 控件 | 行为 |
|---|---|
| `预设段 k/n`（值按钮，点一下循环） | 选择本层第 k 段 |
| `上移` / `下移` | 只在本层内移动选中的段 |
| `删除第 k 段` | 删除选中的段 |
| `＋ 加为下一段` | 把**当前参数描述的预设**追加到本层末尾（与镜头同一个形状：与 `应用预设层`、`撤销上次修改` 同排的大按钮，三等分） |
| `应用预设层` | 一次事务写整层（`ApplyLayersOnMainThread`），替掉了原来的 1:1 `PreviewUpsert` 写入 |
| `清空本层` | 清空整个层，**作为待应用改动**（原来"清除本槽动作"是立即写入的，现在统一走应用） |
| 窗口顶部一行 | `预设 3 · 本层 2 段 · 共 1.60 s`——**由同一个栈产生**，与详情页不可能不一致 |

会话（`CharacterPresetEditorSession`）持有这个栈：它本来就 4 Hz 轮询该行，现在顺带把 `preset:{slot}` 灌进栈；**有未应用改动时不重读**（不会冲掉正在叠的东西）。切换目标槽位会重建栈（层是按槽位标识的）。

删掉的东西：`EffectLayerReader`（窗口那条摘要行原来自己读共享事务，现在会话提供）、`CharacterPresetEditorSession.Apply()` 与 `ClearPreset()`、`EditorCommandDocumentService.ApplyRemovePresetSelectedOnMainThread`——预设家族现在**只有一条写入路径**。

### 8.3 实机验收点

1. 预设窗口下方出现：`[预设段 0/0][上移][下移]`、`[删除这段]`；底排三个大按钮 `[＋ 加为下一段][应用预设层][撤销上次修改]`（未应用时 `应用预设层` 才可用）。
2. 调好参数 → `＋ 加为下一段` → 顶部一行变成 `预设 N · 本层 1 段 · 共 …`，段号按钮变 `预设段 1/1`。
3. 换个动作再 `＋` → `本层 2 段`；`上移/下移/删除` 只动本层；`应用预设层` 写入，播放这一句应看到**两个预设按顺序播放**（同一 `preset:{slot}` 轨追加）。
4. `清空本层` 只是标记，按 `应用预设层` 才真的删掉那一层的行。
5. 回归：人物模式、屏幕文字模式的"应用草稿"照旧；`撤销上次修改` 仍能撤销整层写入（走同一条共享事务撤销链）。

### 8.4 人物层（`character:{slot}`）也接上了（同日，第三部分）

最后一个已知缺口。画面编辑器的**人物模式**现在拥有当前选中角色的那一层，形状与镜头模式完全一致：

| 控件 | 行为 |
|---|---|
| `角色段 k/n`（点一下循环） / `上移` / `下移` | 选择并调整本层顺序 |
| `删除第 k 段` | 删除选中的段 |
| `＋ 加为下一段`（底排大按钮） | 把当前草稿追加到**当前选中角色**那一层；同一个按钮在镜头/人物两种模式下各加各的层 |
| `应用角色层`（原「应用草稿」） | 一次事务写整层；有未应用改动时标签带 `*` |

### 9.1 实机发现的缺陷：人物模式的层行压在「复位/清空」上（同日修复）

用户反馈：立绘操控（画面编辑器的人物模式）的层编辑器**与旧 UI 重叠**。

根因是一个**入参含义搞错**，不是坐标写错：`LayoutCharacterLayerControls` 的形参意思是"本模式把 复位/清空 放在哪一行"，而人物分支传的是 `resetRowY`。在人物模式里这两行不是同一行——

| 行变量 | 人物模式放的东西 | 镜头模式放的东西 |
|---|---|---|
| `resetRowY` | `r0`（旋转复位）/ `翻转复位` | `camera-reset` / `camera-clear` |
| `actionY` | `reset`（整体重置·回归官方槽位）/ `clear`（清除草稿） | （空） |

于是段选择行落在 `actionY` 上，**正好压住「整体重置·回归官方槽位」和「清除草稿」**，删除行又占了原来「连续对话」的位置：整块比预期高一行（50 px）。镜头模式传的 `resetRowY` 恰好就是它自己的 复位/清空 行，所以那边一直是对的——这也是这个错误能躲过前面几轮的原因。

修复（三处，都是"把意思写对"）：
1. 人物分支改传 `actionY`（`LayoutCharacterLayerControls(actionY, rowGap)`）。
2. 两个 partial 的形参改名 `resetClearRowY` 并加 `<param>` 说明：**要传按钮实际所在的那一行**。
3. 删掉 `Layout` 里多出来的另一个 `LayoutCameraLayerControls(dialY, rowGap)`：它先把镜头行摆在 时长/缓动 与 `camera-reset/camera-clear` 上，随后又被三元表达式里的调用逐个覆盖。当前无可见影响，但它就是下一个同类 bug 的温床（同一组控件被摆两次）。

现在人物模式的行序（自上而下）：`位置` → `x/y` → 旋转盘/角度 → `翻转/时长/缓动` → `r0/翻转复位` → `复位/清空` → **`角色段 k/n` | `上移` | `下移`** → **`删除第 k 段`** → `连续对话`。草稿框高度是从 `continueRowY` 反推的（`continueRowY - 130`，下限 72），所以整块下移不会压到它。

实机验收点：人物模式下 角色段/上移/下移 行不压 复位/清空；删除行不压 连续对话；底排 `＋ 加为下一段` 仍在原位；镜头模式的行序未动。
