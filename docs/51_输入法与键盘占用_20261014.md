# 键盘占用、输入法合成与中文输入（2026-10-14）

用户反馈：**装入模组后无法使用中文输入法；英文可以正常输入，只有中文不行。** 本文记录代码侧的三条相关机制、这次调查的结论边界，以及本批新增的窄开关与日志。

## 1. 我们对输入的接管（全部在进程级）

| 机制 | 位置 | 影响 |
| --- | --- | --- |
| **键盘占用**：任一工具界面要键盘时，对 `UICamera.ProcessOthers`、`UIInput.Update`、`UIInputOnGUI.OnGUI` 的 Harmony 前缀返回 false，跳过官方 NGUI 处理 —— 而 NGUI 的 `UIInput.Update()` 正是游戏输入框读取字符与 `Input.compositionString` 的地方 | `ToolInputService.KeyboardPrefix`、`_keyboardCaptured` | 占用未释放时游戏自己的输入框**中英文都进不去** |
| **输入法合成开关**：工具界面要合成时把全局 `Input.imeCompositionMode` 写成 `On`，并把 `Input.compositionCursorPos` 指到工具的光标；不需要时写回 `Auto`。Unity 在 `On` 下**不再自己绘制合成/候选**，必须由程序绘制 | `ToolInputService.ApplyComposition`；绘制在 `ToolboxDrawer`（读 `Input.inputString` / `Input.compositionString` 自绘） | 只要有一个合成 owner 没释放，游戏自己的输入框会出现"合成在跑但看不见、也提交不了"→ **英文正常、中文打不进去** |
| **鼠标守卫**：指针压在工具区域上时跳过 `UICamera.ProcessMouse` | `ToolInputService.MousePrefix` | 残留区域会吃掉点击，让人点不进官方输入框 |

三条机制都是**进程级**的：不是"只在工具界面里生效"。

## 2. 本次反馈指向哪一条

"英文能打、只有中文不行"排除第一条（否则英文也进不去），指向**第二条：合成开关/合成绘制**。也就是说，症状与"某个 owner 没有及时释放 `SetComposition(owner, false)`"吻合；代码里所有正常关闭路径都有释放调用（`ResetInteraction()`、`HideHostedControls()`、`BeginLevelChange()`、抽屉 `Hide()`、窗口 `Dispose/Hide`、设置窗关闭），**因此这是一条"未复现的怀疑"，不是已确认的根因**：真要定因，需要出问题那次的日志与"英文/中文"的对照。

## 3. 本批新增（两件小事）

1. **状态变化日志**：键盘占用/释放、合成开关切换（`On`/`Auto`）各打一行，含当前 owner 数，最多 40 行：

   ```text
   [input] keyboard captured; owners=1
   [input] composition On; owners=1
   [input] composition Auto; owners=0
   [input] keyboard released; owners=0
   ```

   以前完全没有这类日志，只能靠症状推断；现在"我们什么时候拿走、什么时候还回去"可以直接从日志读出来。

2. **窄开关 `[Input] TakeOverKeyboardAndIme`（默认 true）**：设为 `false` 后
   - 不安装三个 NGUI 键盘前缀（`SupportsKeyboardCapture=false`，搜索框等要求键盘的工具页会自动降级）；
   - 完全不写 `Input.imeCompositionMode` 与 `compositionCursorPos`；
   - **鼠标守卫、工具箱与所有工具页照常工作**。

   也就是说，遇到中文打不进去的用户可以立刻自救，代价只是**工具界面内部**的中文/日文合成不再由我们处理。这是本批唯一面向用户的绕过手段；已发布的 0.4.4 没有这个开关，只能整个停用 RukariLib。

日志另外会打印一行 `input: TakeOverKeyboardAndIme=<true|false>`，便于确认现场配置。

## 4. 定位用的对照（给反馈者）

| 问题 | 指向 |
| --- | --- |
| 游戏自己的输入框里打英文字母能进吗 | 不能 → 键盘占用未释放（第一条）；能 → 合成问题（第二条） |
| 是哪个输入框：游戏自己的，还是工具里的搜索框 | 后者说明只是我们自己字段的合成绘制，与全局无关 |
| 候选窗会出现吗？位置对吗 | 位置错/不出现 → `compositionCursorPos` 或 `On` 残留 |
| 装的是哪几个模组、哪个 AA 版本 | PE 上 `UIInputOnGUI.OnGUI` 不存在、键盘组整体停用（docs/49），症状不同 |
| 只关掉 RukariLib 能恢复吗 | 能 → 归因到 Lib 的输入服务 |
| `[Input] TakeOverKeyboardAndIme=false` 后能恢复吗 | 能 → 确认是键盘/合成接管这一段 |

## 5. 边界

- 本条与 PE 闪退（docs/49、docs/50）是两件事：一个是输入法合成，一个是点开 Script 节点崩溃，不要合并结论。
- 本次没有实机复现，也没有取得反馈者的日志：`TakeOverKeyboardAndIme=false` 是**绕过手段**，不是"根因已修复"。
- 键盘/合成的接管本身是既有设计（工具页需要输入框），本批只增加了"可以关掉"与"能看到什么时候开关"。
