# 动作保持门修复：脚本读取改为接口 + 具体类型两步读取

日期：2026-10-13  
适用版本：AA 1.01，`E:\AA1.01`  
证据日志：`player-command-observation-20261013-005243.log`、`player-command-observation-20261013-010012.log`、`E:\AA1.01\BepInEx\LogOutput.log`

## 1. 现象

正式播放时“只有结果、没有过程”。用户描述：位移从 1 直接到 4，2-3 的结果产生了，但过程被跳过。

## 2. 证据

同一行两条命令各自的 `durationMs=600`，但引擎在毫秒级就推进到下一行：

```text
00:53:30.0813  SCENE_COMMAND_DISPATCHED record=1 slot=3 durationMs=600  beforeX=0        targetX=-748.283
00:53:30.0865  advance-window sequence=18 playbackRow=1->2     仅 5.2 ms 后
00:53:30.0876  SCENE_COMMAND_DISPATCHED record=2 slot=3 durationMs=600  beforeX=-748.283 targetX=40.448 targetZ=-77
00:53:30.0914  advance-window sequence=19 playbackRow=2->3     仅 3.8 ms 后
```

两条都是**空对白**行，靠官方 `#wait;1` 锚点才拿到正式行，锚点只有 1 ms。负责把行撑到动作结束的是 `PlayerActionTimelineRuntime`（`docs/26`）：它把官方 `ScenarioAnimation.WaitAnimation` 插进 `scenarioAnimations`，先给派发一个有限观察窗，动作真正开始后再用真实截止时间重新武装。而它在这一会话里**一次都没有装上**：

```text
action-timeline: installed; official-animation-list; actual-parser-input; native acceptance pending
action-timeline: parse failed: Il2CppException: System.NullReferenceException   x8
--- BEGIN IL2CPP STACK TRACE ---
at Google.FlatBuffers.Table.__offset (System.Int32 vtableOffset)
at FlatData.ScenarioCharacterNameExcel.get_NameTW ()
```

没有 `action-timeline: armed`。异常被自己的 catch 吞掉后直接返回 → 没有 `WaitAnimation` → 行只活 1 ms → 过程被吃掉。

由于 IL2CPP 栈只有两帧原生帧，无法据此判断是哪一次跨原生读取炸的，因此先在 `ParsePostfix` 里加了一个**阶段标记**（`stage=1` 读 `ScriptKr`、`stage=2` 读 `owner.cur`、`stage=4` 启用检查、`stage=7` 计划、`stage=9` 动画列表、`stage=11-12` 新建与加入 `WaitAnimation`、`stage=14` 武装）。该构建行为一字未改。下一次实测结果：

```text
action-timeline: parse failed at stage=1; row=-1; preview=False; scriptLength=-1; Il2CppException: ...
```

`stage=1` 且 `row=-1`、`scriptLength=-1`：**异常发生在读取 `scenario.ScriptKr` 这一句**，读取 `owner.cur`（原顺序在它之后）尚未执行。

## 3. 根因

`IScenarioScriptExcel` **接口**方式调用 `ScriptKr` 会抛原生 NRE，而同一个属性通过**具体类型** `GenericScenarioExcel` 转换后可以正常返回。这不是新发现：`ContinueDialogueRuntime.TryReadScriptKr` 早就在用「先接口、失败后具体类型转换」的两步读取（`ContinueDialogueRuntime.cs:386`）。

而 `PlayerActionTimelineRuntime.ParsePostfix` 只在第一步就读 `scenario.ScriptKr`，一抛就整段放弃 → 保持门永远装不上。这条路径在 1.5.5 时期可用（`docs/26` 期望看到 `armed`/`released`），之后引入的锚点与额外 `ScriptKr` postfix 改变了这个 getter 的行为，使它不再能从接口调用成功。

## 4. 修改

- `src/AzureArchive.VideoTools/Runtime/ContinueDialogueRuntime.cs`
  - `TryReadScriptKr` 由 `private` 改为 `internal`，加注释说明两步读取的原因，供动作时间轴复用。
- `src/AzureArchive.VideoTools/Runtime/PlayerActionTimelineRuntime.cs`
  - 新增 `ReadScenarioScript`：走共享的两步读取；两次都失败时只报一次日志并返回空串，**不再让整段放弃**。
  - 读取顺序改为先 `owner.cur`、再脚本，便于失败定位。
  - `sequence` 语义保持不变：能读到脚本时仍以 `CaptureParsedScript` 的返回值为准（同一窗口内出现冲突输入时依然拒绝装门）；只有读不到脚本时才退回当前活动窗口序号。
  - 保留全部阶段标记与失败日志，日志增加 `scriptKnown`。
- `src/AzureArchive.VideoTools/Runtime/PlayerCommandObservationRuntime.cs`
  - `GetTimelinePlan` 正式播放分支：脚本为空且行号有效时改用 `PlaybackAdvanceDispatchPolicy.ObserveEmptyFormalRow`（与派发器对“窗口未携带托管身份”所用的同一套 fail-closed 规则），仍然只在该行确实持有一个批次时给出计划。

### 安全性

- 装门的判定不变：只有真正持有指令批次的行才会插入 `WaitAnimation`；无指令、歧义、多记录一律不装。
- 观测窗上限仍是 `DispatchTimeoutSeconds = 10 s`，动作开始后按真实截止时间加 3 s 诊断余量重新武装；失败不无限卡住播放（`ActionTimelineCompletionGate`）。
- 未改排队语义、未改派发、未改身份计算、未改 AAP/AAS。

## 9. 补刀：冷保持门被“绑定工程引发的重载”清掉（2026-10-13 修）

### 9.1 现象

用户反馈：**开着 AUTO 直接进剧情会丢指令，手动点第一行就没问题。**

### 9.2 证据

日志 `player-command-observation-20261013-110206.log`（11:03:42 那次进剧情）：

| 时刻 | 事件 |
| --- | --- |
| .7179 | `auto-discover status=READY; … rootSource=official-playback-resource-path; storageRevision=11`（**绑定由播放路径触发**） |
| .7185 | `playback-pair-discovery sequence=18; row=0` → `observation sequence=18; status=INDEX_PENDING_ACTION_HOLD; action=DEFER_CURRENT_ROW`（冷保持门＋待补发凭证） |
| .7197 | `dialog-continue context-invalidated; source=index-reload` |
| .7203 | `index-reload accepted=true; …` ← 旧实现在这里把凭证和保持门一起丢掉 |
| .7478 | `index-load status=READY` ← 索引到了，但没有任何人再补发 |

全日志没有 `QUEUED_SCENE_COMMANDS sequence=18`、没有 `SCENE_COMMAND_DISPATCHED … sequence=18`；BepInEx 侧该序列仍然 `action-timeline: armed; sequence=18; row=0; preview=False; cold=True` → `released; status=Completed`，是**空完成**。同一形态在 10:26:32 那次会话也出现过（hold `.3018` → `index-reload accepted=true` `.3220` → READY `.4303`），因此不是本轮改动引入的。

### 9.3 根因

`PlayerActionTimelineRuntime` 的冷保持门（`cold=True`；`_coldHoldUsed` 每次会话只允许一次，`PlayerActionTimelineRuntime:107/119-121`）依赖 `_pendingTimelineWindow` 这份“待补发凭证”；而 `ConsumeIndexReloadRequest` 在重载时把凭证与门一起清掉。绑定工程的人（auto project discovery）恰恰是在**这一行**上完成绑定并请求重载的——凭证只活了 2 ms，之后 `DrainPendingTimelineWindow` 没有凭证可跑，这一行的指令再也不会派发。

### 9.4 为什么 AUTO 中招、手动没事

由**绑定工程的时刻**决定。`rootSource=official-playback-resource-path`（开 AUTO 直接进剧情就是这条路径）时，本次会话的第一次场景解析就是剧情第一行，绑定/重载正好压在这一行的保持门上；手动先经过编辑器（`rootSource=official-project-resource-path`）时，绑定/重载发生在那一行之前，那一行装门时已经有索引（`cold=False`），同帧直接派发，根本不需要补发。

### 9.5 修改

1. `ConsumeIndexReloadRequest` **不再丢** `_pendingTimelineWindow`（删掉 `ReleaseUnclaimed` 与置空两行），交给 `DrainPendingTimelineWindow` 自己的守卫判定；
2. 该路径两种结局都打日志，消灭静默：
   - `pending-timeline resumed; sequence=<n>; stage=<stage>`
   - `pending-timeline dropped; sequence=<n>; reason=<call-chain-aborted|storage-changed|owner-or-row-changed|index-load-failed>; writes=false`

守卫顺序：`call-chain-aborted` → `storage-changed`（`BelongsToStorage`）→ `owner-or-row-changed`（`CanResume`，措辞与运行时自身的 `Forget("owner-or-row-changed")` 一致）→ `_index == null` 时继续等，只有 `_lastFailedIndexLoadSignature != null`（加载确实失败）才丢。

### 9.6 安全性

- 保留的窗口不会悬空：`CanResume` 要求持有者、当前行、预览模式、存储修订全部未变；行一旦被推进或引擎换行，下一帧就以 `owner-or-row-changed` 丢弃并打日志。
- 索引加载失败 → `index-load-failed` 丢弃；`_index` 既没成功也没失败时，保持门自身的派发超时（`DispatchTimeout` → `Forget("native-animation-never-started")`）兜底，不会永久占住一行。
- 派发仍走同一套授权与捕获校验（`conflicting-embedded-command-captures` 等）；新索引只是换了一份判据，没有放松任何一条。
