## 1. 问题与证据

正式播放日志 `player-command-observation-20261013-003229.log` 中，同一行的两条命令在 **17 ms** 内先后派发到同一个槽位：

```text
sequence=2 record=1 slot=3 durationMs=600
sequence=3 record=2 slot=3 durationMs=600
```

当前实现是“立即写入目标状态”。同一槽位的后一条命令直接覆盖前一条的目标，于是动画过程被吃掉，只剩下最后一个结果。用户观察到的现象正是如此：

> 空对话的等待时间所导致的过程没有出现，但是结果出现了。

官方不是这样。官方效果是**自带寿命的对象**，彼此不共享一个可变目标，因此可以真正并行或叠加：`AddBubbleDuration`、`AddBubbleType`、`AddBGChallenge…` / `AddBGEffect`、`AddEffect`、`AddDelay`、`AddOutputDelay`、`CharacterFadeTask`、`BGMFadeOutTask`、`TextFadeInTask`、`set_bgShakeTween`、`TextTypewriterAnimation`（`Complete` / `Cancel`）。官方只有 `#wait` 会占住一行（走 `DelayedAdvance` 异步状态机）。

结论：要把“同一槽位的多条动作”从**最后一次写入**改成**轨道上的排队事件**。

## 2. 语义（已确认）

### 2.1 默认排队

同一槽位在一次播放行内收到的多条动作，默认按到达顺序**追加**到该槽位的时间轴上：第 n 条在前一条**结束之后**开始，而不是覆盖它。`duration=0` 的瞬时设置仍然立即生效，不占用时间，也不阻塞后续段。

理由：

- 关键帧的本质是“轨道上的键序列”，只有追加能无损升级到后续的关键帧编辑器；
- 与自家 `#aavt;spine` 的 `track=20..29` + `blend=replace|add` 同构；
- 官方 fire-and-forget 在“单个可变目标”上的等价物就是排队。

### 2.2 显式参数

| 参数 | 含义 | 本阶段 |
| --- | --- | --- |
| `at=<ms>` | 从本行动作时间轴起点算起的显式偏移，用来让同卡两段错开，**不再依赖 `#wait`** | 实现 |
| `interrupt=true` | 显式打断：立即取消该槽位当前段并接管（等价于今天的行为） | 实现 |
| `layer=` / `blend=replace\|add` | 与其他 Mod / 官方写入的叠加规则 | 只实现 `replace`；`add` 留待后续 |
| `keys=<t>:<v>,…` | 手写关键帧 | 不解析；出现即报错拒绝，避免作者误以为生效 |

### 2.3 强制推进 = 快进到终点

我们**不给官方推进装闸门**：`Test.AdvanceScenario` 不会被我们拦住。当玩家或 AUTO 在本行动作还没走完时推进到下一行：

1. 本行剩余段**立即跳到自己的终点状态**，保证作者写下的终点一定成立；
2. 绝不允许“丢弃剩余段”：`move;dx=` 是**相对**累加，丢弃会留下作者没有定义过的中间态，并污染后续的继承基线；
3. 诊断日志：

```text
queue-forced-finish; remainingMs=<剩余毫秒>; segments=<剩余段数>
```

第一版实现为**立即跳到终点**（不做加速收尾）。后续可加 `fastForward=animate|instant`，默认 `instant`。

### 2.4 预算与上限

单行单槽位排队总时长上限默认 3000 ms（`ActionQueueBudgetMs`）。超过预算时只执行到上限，并在诊断里报 `queue-over-budget`，不静默丢弃也不无限拖长这一行。

> **2026-10-14 修正**：上限改为 **10000 ms**（`SlotActionQueuePlanner.DefaultBudgetMilliseconds`），理由见 [`docs/45` §10.3](45_镜头窗口与层写入_20261013.md)：3 秒比作者实际写的编排短——五段转身加一次镜头就是 3.6 s，于是镜头正好落在上限上被折叠成 0 长度、**当帧跳到终点**，看起来就像"镜头第一步就跑了"。另外本节提到的 `ActionQueueBudgetMs` / `ActionQueueEnabled` 两个配置项**从未实现**（代码里没有这两个键），上限一直是常量。

## 3. 边界：这个阶段不做的事

- **不给官方推进装闸门**，不拦截也不主动调用 `AdvanceScenario`（沿用 `docs/26` 第 5 条）。
- **不在编译边界合成 `#wait`**。那会改 `OfficialText` → 改 `CompiledScriptIdentity` → 破坏 AAP↔AAS 映射与预览身份。空对白的 `#wait;1` 锚点（`docs/37` §3.1）只服务“完全空对白”，不得被借用来实现排队。
- **不新增官方动画类，不替换官方播放协程**；继续使用官方动画列表和 `ScenarioAnimation.WaitAnimation` 桥接（`docs/26`）。
- 队列只在**已经授权的派发**之后生效；未授权、验证失败、租约失效、重复窗口一律不建队。
- **全程 fail-open**：队列规划失败时回退到今天的“立即写入”，并在诊断里标明原因，而不是卡住播放。

## 9. 前提修正与放行决定（2026-10-13，用户已确认）

### 9.1 修正后的前提

原本把 2a 描述为「修同一槽位后段覆盖前段」。**实测与代码核对后不成立**：今天「同一张卡里对同一槽位写两段动作」是被**两层 fail-closed 拒绝**的：

```csharp
// 编译期：整档失败
// Core/Commands/CommandTimelineCompiler.cs:344-362

    → Fail($"Scene {location} contains more than one enabled command for public slot {…}.")

// 运行期：该批次被拒
// Core/Commands/PlaybackSceneDispatchGate.cs:136
```

`CommandResourceIdentity.KeyFor` 把两条 `#char;3;…` 都映射为 `"character:3"`（`#fx;3` → `"preset:3"`；同 scope 的 `#camera` → 同一相机 key）。因此编译期那条会让**整个工程**在播放里一条命令都不出现——这是继 §4 的映射放大器之后的**第三个整档失败放大器**，而且触发动作极其自然（同一角色写两次 `set`，或 `set` + `move`）。

### 9.3 放行决定（用户已确认）

**把「同一张卡里对同一槽位写多段动作」变成合法 + 排队。** 即：编译期改为按槽位产出**有序段**（保留列表顺序、不再拒绝），运行期 `ValidateBatch` 不再拒绝重复槽位 key，并由 `SlotActionQueuePlanner` 给出的 `StartMs` 决定每段何时落地。

- 这确实是放宽两层 fail-closed 规则，属于用户明确拍板的范围变更；

## 10. 预览与正式播放一致（2026-10-13 完成）

### 10.1 问题

预览派发（`DispatchEditorPreview`）原本有**自己的一条同帧循环**，逐条应用命令，**不经过**队列 ⇒ 同一张卡的两段在预览里仍在同一帧落地（只有终点、没有过程），而正式播放已经分段。这正是「编辑器里看到的和播放出来的不一样」。

### 10.2 做法：一份决策，两条路径共用

`Runtime/SlotActionQueueRuntime.cs` 新增 `SlotActionQueueDeferral.Decide(directives)`：返回 `SlotActionDeferralDecision(Plan, Error, SameFrameIndices, DeferredIndices)`。播放的 `EnqueueDeferredSegments` 与预览的 `EnqueueDeferredPreviewSegments` **都只调用它**，因此「哪一段现在落地、哪一段等时间轴」在两条路径上不可能分叉。`Plan` 为 null 表示这一行不需要队列（不足两条命令）或规划失败——两种情况下调用方保持今天的同帧行为（fail-open）。

预览侧的接线方式刻意做成**最小侵入**：`DispatchEditorPreview` 增加一个可选的 `PendingPreviewSegmentContext? continuation` 参数，循环头由 `for (…; index < queued.Commands.Count; …)` 改为 `foreach (int index in indices)`，**循环体一字未改**（`continue`/失败 `return` 语义原样保留）。续段落地时复用的是：

- 同一条 `DispatchEditorPreview` 路径（因此沿用同一套资源/基线/链式写入，**无新旁路**）；
- 授权它的那次 dispatch 解析出的 `chain`（存入预览段上下文）；
- 该预览已经持有的资源集合（续段只做并集，后续 cleanup 仍能释放整张卡触碰过的东西）。

而被续段**跳过**的只有三处，都以守卫实现、不改动任何既有行：

| 跳过项 | 为什么 |
| --- | --- |
| `ObserveDialogueBoundary` + `StopAll("authoritative-preview-replay")` | 续段属于同一次重播，不能重置第一段正在动画的姿势 |
| 上一张预览的 cleanup | 同一次预览还在进行中 |
| 链式应用与继承相机起点 | 会在队列中途二次写入 |

保持门无需改动：`GetTimelinePlan` 的 `max(ParallelDuration, 队列 TotalMs)`（`:165-183`）在 preview/playback 两个分支**之后**统一生效，因此预览也已覆盖队列总时长（本轮核对确认，未改代码）。

排空顺序也已有保证：`DrainQueuedSegments`（`:689`）位于 `DrainDeferredEditorPreviews`（`:679`）之后、`PlayerActionTimelineRuntime.TickAfterRendering`（`:692`）之前——本帧到期的段先延长 `DueAt`，保持门随后才判断这一行是否结束。

### 10.3 关键安全决定：续段落地前**必须重新校验租约**

续段在点击之后 600 ms 才落地，而**这段时间里作者可以点另一行**。原预览路径在进入 dispatch 前会跑 `EmbeddedEditorPreviewLeaseCache.IsCurrent(...)`，但没有任何机制覆盖「已授权、稍后落地」的续段。

**决定：续段落地前用同一个 `IsCurrent` 重新校验；不通过就丢弃该序列剩余段且不写任何东西**，打 `queue-segment-dropped … reason=<drift>; writes=false`。

这与正式播放的「强制推进=快进到终点」**有意不同**：播放里那一行是权威的、引擎不会中途换场景；预览里作者随时可能切走，而把已被顶替场景的终点写进当前活动槽位，正是预览路径处处禁止的事（`old-scene-character-baseline-must-not-write-current-live-slots`）。同理，新的点击会顶掉上一张预览的尾巴（`queue-preview-superseded`），同样是**丢弃不写**。

### 10.4 夹具

`SlotActionPreviewQueueTests`（4 条）：同槽位两段 ⇒ 第一段同帧、第二段 `StartMs == 600` 入队且顺序保持；单段预览 ⇒ **无计划**（`Plan == null`）、恰好 1 段、`StartMs == 0`、队列为空；不同槽位 ⇒ 全部同帧、不入队；混入 `#wait;100` 之类不被调度的指令 ⇒ 不影响已调度指令的顺序。

## 12. 相机续段跳过 replay-restore（2026-10-13 修）

### 12.1 现象与证据

工程 `测试-时间轴2` 行 3（台词 "3"）：`#aavt;camera;move;dx=200;duration=600;easing=linear` ＋ `#aavt;camera;move;dx=60;duration=400;easing=linear`（同一条 `camera` 轨道、同一 scope）。实测（`player-command-observation-20261013-121123.log:800-804`）：

```
queue-segment index=0 startMs=0   durationMs=600 placement=append
queue-segment index=1 startMs=600 durationMs=400 placement=append
SCENE_CAMERA_DISPATCHED order=0 … baselineCaptured=True;  replayRestored=False; beforeX=0; targetX=200
SCENE_CAMERA_DISPATCHED order=1 … baselineCaptured=False; replayRestored=True;  beforeX=0; targetX=60
```

第二段在应用前做了一次 **replay-restore**：把该 scope 拉回本行场景入口（X=0），再从入口算 `dx=60`。结果相机停在 **60** 而不是 260，视觉上还会看到 0→200 之后被拉回 0 再走到 60。

### 12.2 根因

`SceneCameraService` 对「同一 (场景, scope) 的第二条及以后」总是规划 `PlanReplayRestore`——这是**故意**的：它让一行的重播幂等（`Contracts.cs:399-406` 的注释正是为此）。但队列的**续段**不是重播，它是同一行同一条动作轨道上的下一段，按 §2.1/§2.3 必须**累加**（相对 `dx` 也是"绝不丢段"这条规则的理由）。人物路径早已为续段关掉了这件事（`CharacterTransformDispatchRequest.RestoreSceneBaseline=false` → `replay-restore-suppressed`），相机路径此前没有这个开关。

### 12.3 修改

- 新增兄弟契约 `ISceneCameraContinuationService`（`Rukari.MoreEffects/Api/Contracts.cs`）：冻结的相机契约不能加成员，这与既有 `IScopedSceneCameraService` / `ISceneCameraCommandDispatcher` 的做法一致；
- `SceneCameraService.ExecuteOnMainThread` 拆成 `ExecuteCore(…, restoreSceneEntry)`，续段入口传 `false`；预览清理用的 `#camera;reset` 仍走默认（`true`）；
- 播放与预览两条派发路径各自识别"同一 scope 的后续指令"（新增 `CameraScopeSlotOf` / `HasEarlierCameraInstructionOnScope` / `HasEarlierPreviewCameraCommandOnSlot`，与人物那三个同名助手对称），命中时改走续段入口。

### 12.4 边界

- **一行的第一条相机指令仍然 restore**（`baselineCaptured` / `replayRestored=False` 语义不变），因此整行重播依旧幂等——续段跳过 restore 的前提正是"前一段已经把入口变成它的终点了"。
- 不同 scope 互不影响（`resourceSlot` 区分）；人物与相机互不影响。
- 相机行的日志字段不变，续段现在会显示 `replayRestored=False; beforeX=<实时值>`，与人物路径的 `replay-restore-suppressed` 等价。

### 12.6 被顶掉的保持门：剩余段漂到后面的行（2026-10-13 修）

**现象（`player-command-observation-20261013-121953.log`，快速连点）**：行 1 的计划是 0–300 与 1500–1800，作者在 ~430 ms 点了下一行；上一行的保持门被下一行的 arm **直接覆盖**，既没有 `cancelled`/`released`，也没有快进，于是那段 `at=1500` 的相机段**按绝对时间在 1.5 s 后落地**——此时行 2 已经算完自己的镜头：

```
（行 2 自己）SCENE_CAMERA_DISPATCHED sequence=28; order=0 … beforeX=200; targetX=400
（行 2 自己）SCENE_CAMERA_DISPATCHED sequence=28; order=1 … beforeX=400; targetX=460
（行 1 的残留）SCENE_CAMERA_DISPATCHED sequence=26; record=0; order=1 … beforeX=460; targetX=520
```

同一轮里 seq 26/27/28 三个保持门都没有收尾行（只有行 3 因为下一行是空行、没人 arm，才跑到 `cancelled; owner-or-row-changed`）。

**根因**：`PlayerActionTimelineRuntime.ParsePostfix` 装新门时 `Gate.Cancel()` 直接覆盖旧状态，`Forget` 永远没机会跑；队列按绝对截止时间独立运行，于是残留段落进了后面的行。

**修法**：arm 时若上一道门还活着且 sequence 不同（且上一道是播放门，预览门有自己的"离开就不写"语义），只把它**记入** `_supersededSequences`；紧接着的 managed update 在**任何派发之前**调用 `FlushSuperseded()`，逐个打 `action-timeline: superseded; sequence=<n>; reason=next-row-armed` 并 `FastForwardQueuedSegments(sequence, "superseded-by-next-row")`。

三个"不能"：不能在 native parse 里直接写 transform（场景正在换）；不能拖到 `TickAfterRendering`（那时新行指令已经写完，旧端点会盖在新行结果上）；不能丢段（§2.3：相对 `move;dx=` 丢段会留下作者没写过的中间态并污染继承基线）。放在派发之前，旧行端点正好**垫在**新行指令下面，也就是"下一行继承端点"。

**验收**：同一张卡快速连点（在 0.5–1.4 s 之间点），应看到 BepInEx `action-timeline: superseded; sequence=<n>` ＋ 诊断日志 `queue-forced-finish … segments=1; action=APPLY_END_STATE_NOW` ＋ `queue-forced-segment … instant=true`，相机立刻到 **260**，且后面不再出现 `sequence=26` 的残留派发。

### 12.7 强制推进的测试设计教训

`queue-forced-finish` 只对**还在队列里**的段生效。第一次测卡 B 时点击落在 641 ms，而第二段在 +300 ms 就已落地（队列为空），所以既没有 `queue-forced-finish` 也无需快进——不是失败，是没打中。要打中，必须让**点击发生在某段尚未落地时**：把该段的 `at=` 推远（例如 1500 ms），在 0.5–1.4 s 之间点下一行。

## 13. 保持门覆盖"整行计划"（2026-10-13 修）

### 13.1 现象与证据

`player-command-observation-20261013-122624.log` 行 1：`camera;move;dx=200;duration=300` ＋ `camera;move;dx=60;duration=300;at=1500`。第二段**没有等到 1500 ms**：

```
SCENE_CAMERA_DISPATCHED order=0 … durationMs=300; beforeX=0; targetX=200        (31.381)
queue-forced-finish sequence=10; reason=Completed; remainingMs=1149.4974; segments=1; action=APPLY_END_STATE_NOW   (31.684)
queue-forced-segment sequence=10; slot=camera; index=1; appliedMs=0; instant=True; reason=       (31.686)
SCENE_CAMERA_DISPATCHED order=1 … durationMs=0; beforeX=200; targetX=260        (31.688)
```

第一段一跑完（+303 ms），门就判定本行结束，把还在队列里的第二段当"剩余段"瞬时落地。作者写的"1.5 s 后再动"被压成瞬时跳。

### 13.2 根因

`GetTimelinePlan`（`PlayerCommandObservationRuntime.cs:146-189`）**已经**算出 `max(ParallelDuration, 队列 TotalMs)`，注释里也写明"保持门必须覆盖整条槽位队列"；但 `ParsePostfix` 只用了它的 `HasCommands`，`Seconds` 从来没进过门。门的截止时间只来自"已经派发出去的动作"（`AddCharacter` / `AddCamera` / `AddPreset` → `Gate.AddAction(dispatchTime, duration)`），所以任何"偏移超过前一段结束"的间隔型 `at=` 都会被压掉。

`at=300` 这类"偏移落在前一段之内"的用法不受影响：第二段到期时第一段还没跑完，门自然还活着（已实测）。

### 13.3 修改

第一版（`572AA52AA9099948`）在 `ParsePostfix` 里记 `_plannedSeconds = plan?.Seconds ?? 0d`，`BeginDelivery` 时补进门口——**实测无效**：第一行是 `cold=True`（索引还没到，`plan is null`），记下的是 0，`remainingMs=1130.5` 依旧（`player-command-observation-20261013-123146.log:67`）。

第二版（`946E8CA0BBDEA066`）把总时长挪到**交付时**计算：

- 抽出 `PlannedSecondsOf(canonicalDirectives)`（`PlayerCommandObservationRuntime.cs`）= `max(ParallelDuration, 队列 TotalMs)`，与 arm 时的 `GetTimelinePlan` **共用同一条规则**；
- `PlayerActionTimelineRuntime.BeginDelivery(sequence, plannedSeconds)` 增加参数，两条派发路径各自从自己的批次算：预览用 `queued.Commands`，播放用 `queued.Batch.Commands`；
- `BeginDelivery` 里 `Gate.AddAction(sequence, Now(), plannedSeconds)`。

这样无论 arm 时有没有计划（冷行/热行），保持门都覆盖整行。教训：**任何"arm 时算一次"的量在冷行上都是 0**，计划类信息必须能从批次本身重算。

### 13.4 边界

- 门的截止时间取 **max**，所以这条只会**延长**保持门，绝不会缩短任何既有卡片的行时长；
- 无命令的保持门走 `ReleaseUnclaimed`（直接 `BeginDelivery` + `Seal`，不经过 `BeginDelivery` 包装），仍是**立即释放**，不会被这条拖长；
