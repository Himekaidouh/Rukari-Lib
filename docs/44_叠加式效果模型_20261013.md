# 叠加式效果模型：撤销关键帧，改为"每窗口管自己那一层"（2026-10-13）

用户的决定：**删掉关键帧功能**（多数用户用不上，而且与其它功能冲突），改为**叠加式**模型——把"应用效果"拆成三段：**选择效果 → 覆盖效果 → 应用效果**；**每个窗口各自负责自己那层效果**。

本文记录：① 这个决定与现有实现的关系；② 已经就是这个形状的部分；③ 需要新增的最小写接口；④ 仍需用户拍板的点；⑤ 建议的第一步。

## 1. 与现有实现的关系

**运行时的轨模型已经是"层"**（`docs/38`，已实机验证）：

- 轨＝资源：`char:{slot}`（每槽一条）、`camera`（全画面一条，含 background scope）、`preset:{slot}`（每槽一条）。
- **预设轨可以跨人物轨**（规划器原文："Only the preset track may cross the others in time"）——也就是说"叠加/并行"在**播放侧本来就有**。
- 同轨默认**追加**；`at=<ms>` 显式偏移；`interrupt=true` 接管该轨剩余时间（两者互斥并明确报错）。
- 行的保持时长＝`max(ParallelDuration, 队列 TotalMs)`，由保持门覆盖（`PlannedSecondsOf`）。

结论：**播放语义不需要为新模型改动**，它本来就是"一层一层叠上去"。

**写入路径**（`docs/38`/`docs/42`）：各页面通过共享编辑事务对 `additionalPrompt` 做**整文读改写**，带 token + revision 双重核对与共享撤销。跨资源写互不影响（各改各的那一行）；**同一资源被两个页面写才会互相覆盖**——这正是用户说的"功能冲突"。

**"一资源一指令"是编辑器页的编辑规则，不是文档格式限制**：`EditorCommandDocumentComposer.Read` 拒绝同资源多条（`docs/42` §3），而 `EmbeddedAavtDirectiveExtractor` 按作者顺序接受多条，播放与只读时间轴都用后者。

## 2. 这个方向省掉了什么

- **不需要跨层段级寻址**，因此 **`docs/42` §6.2.1 的 N 段文档模型（选项 B）不需要做**。
- **不需要自由关键帧编辑**（`docs/34` 阶段 5 的"编辑"半）：`at=`/`interrupt=`/时长/曲线不再需要在时间轴上逐段编辑。
- 时间轴窗口保持**只读**（已交付）——它就是"看这些层叠成了什么"的视图。
- 冲突面收敛到"**同一层**"，而同一层的读写都发生在**同一个窗口**里，天然串行。

## 3. 需要新增的最小写接口

现状：`PreviewUpsert` / `PreviewRemove` **按资源键**定位，一次一条指令。这对"一个窗口管一层"已经够用，除了**一层里要写多段**的情况（例如镜头：先移动 300ms，再在 +1500ms 移动 300ms——这正是 `docs/38` §13 实机验证过的那张卡）。

需要的补充（仍**只在单层内**，不做跨层寻址）：

```
Result<EditorCommandEditPreview> PreviewReplaceResource(
    string sourceText, string expectedRevisionSha256, string resourceKey, IReadOnlyList<string> directives)
```

语义：把 `resourceKey` 这一层在本文档里的**全部行**替换为给定的有序若干条（0 条＝删除该层）；其余行逐字保留；`read` 的 1:1 规则不变，立绘操控页行为不变。

## 4. 仍需用户拍板的点

1. **三段的边界**，特别是"覆盖"指什么：
   - (a) 本层**本行不写**＝继承上一行的值；**写了**＝覆盖该层在本行的值（这是今天的语义）；
   - (b) 本层覆盖**别的窗口**的层（跨层优先级，需要定义谁压谁）；
   - (c) 本层显式**压制/清除**基值（例如预设的"复位"）。
   我倾向 (a)＋(c)，因为 (b) 会引入一份"层优先级表"，而运行时目前没有这个概念（同轨是追加，不是覆盖）。
2. **同一层内多段**：窗口如何表达"我这层有两段"——追加、还是替换整层？（对应 §3 的接口。）
3. **删除范围**：`PresentationTimeline*`（Core 里的归一化模型，含 `PresentationTimelineKeyframe`）目前**没有任何运行时消费者**，约 1000 行 + 6 项测试。既然关键帧不做，是否一并删除？（我建议删：留着会让后来者以为存在关键帧链路。）
4. **层的清单与归属**：`char:{slot}` / `camera`（overall ＋ background）/ `preset:{slot}` / spine overlay / 屏幕文字 / 语音——哪些算"层"，**哪个窗口负责哪一层**。这份归属表是新模型的地基，也是"每个窗口管自己"的可执行定义。
5. `docs/34` 阶段 5 的改写：把"关键帧编辑器"改为"层视图 + 每层窗口自管"。

## 5. 建议的第一步（不需要新接口）

1. 写下**层归属表**（哪个窗口负责哪些资源键）——一行一个资源键，归属唯一。
2. 让每个窗口的写入路径**只动自己的资源键**（今天 `PreviewUpsert` 已经按资源键定位，所以这一步只是把"归属"显式化并加一条断言/日志）。
3. 时间轴面板保持只读，作为"层叠加结果"的视图；在它的轨道头里显示**层归属窗口**（例如"镜头 ← 镜头操控窗口"）。
4. 之后再决定 §4.1 的"覆盖"语义，以及是否需要 §3 的接口。

这样"每个窗口管各自负责的效果"就能在不改播放语义、不做 N 段文档模型的前提下落地。

### 6.1 删掉了什么（净减约 2100 行）

- Core 只读时间轴面板整条链：`TimelinePanel` / `TimelinePanelLayout` / `TimelineRulerLayout`（711 行）。
- MoreEffects 侧：`TimelineApiSource`（75 行）、`TimelineCompanion`（编辑器页自动开关时间轴窗口）、工具箱里的「时间轴」注册项。
- Core 的 `PresentationTimeline*`：`PresentationTimelineBuilder` / `Contracts` / `Validator`（515 行，含 `PresentationTimelineKeyframe`，无任何运行时消费者）。
- 测试：`TimelinePanelTests` / `TimelinePanelLayoutTests` / `TimelineRulerLayoutTests` / `PresentationTimelineTests`（695 行，共 30 项）。

删除的直接理由不是"不好用"，而是**冗余**：在叠加模型里，一行的结果由各窗口自己的顺序决定，时间轴只是用第二套词汇（轨/段/刻度/片段）把同一件事重画一遍，而且它与编辑无关。窗口宿主本身（`docs/42` §1–§2、`docs/03` §5.5）保持不变，预设页仍在窗口里。

### 6.2 换上了什么：层与一行摘要

- `Core/Commands/EffectLayer.cs`：`EffectLayer(ResourceKey, Label, Window)` + `EffectLayerCatalog`。**归属表**：`camera` 与 `camera:background` → 镜头效果窗口；`preset:{slot}` → 预设效果窗口；`character:{slot}` → 更多画面效果页。**一个资源一个写者**。
- `Core/Commands/EffectLayerSummary.cs`：`EffectLayerSummary.Read(layer, 原文)` 用**提取器 + `SlotActionQueuePlanner.PlanDirectives`**（与播放同源，因此多段行可读），按**资源键**把段归到层，输出 `Line`（"镜头 · 本层 2 段 · 共 1.60 s"）与 `LogLine`（`[layer] camera ← 镜头效果 · …`）。
- `MoreEffects/Runtime/EffectLayerReader.cs`：读**共享编辑事务原文**（`IEditorDocumentService.ReadSelection`），4 Hz 缓存，一行一变就记一次 `[layer]` 日志——这是我不用看屏幕也能核对数字的通道，替代了原来的 `[timeline]`。
- 预设效果窗口（`CharacterPresetGroupContent`）在顶部画这一行（`preset.layer.summary`），高度相应 +26，其余内容整体下移，不与任何控件重叠。

### 6.3 两个必须记住的语义决定

1. **`共 X.XX s` 是本层自己的长度**＝本层最后一段的结束减本层第一段的开始，**不是它在轨上的完成时刻**。两处会分叉：两个镜头 scope 共用规划器的同一条 `camera` 轨（先整体 800ms 再背景 300ms ⇒ 轨上总时长 1100ms，但背景层报 300ms）；`at=` 偏移同理。理由：窗口只能对自己那层负责，"我这一层多长"是它能回答的问题，"从第几毫秒开始"是整行的事实。这条语义有测试钉住（`EffectLayerSummaryTests.TheTwoCameraScopesAreTwoLayersOfOneWindow`）。
2. **时间轴删除不影响播放语义**，也不需要新的写接口：预设窗口今天仍走 `PreviewUpsert`（资源键定位，1:1 成立）。**只有"一层写多行"需要新接口**（§3 的 `PreviewReplaceResource`），它随镜头窗口一起落地，不提前引入无消费者的 API。

### 6.4 下一步：镜头窗口（窗口即层的第一例）

> **已落地（同日）**：镜头窗口、`PreviewReplaceResource` 与以提取器校验的写入路径都已实现并部署，细节见 [`docs/45`](45_镜头窗口与层写入_20261013.md)。下面三条是要点的原始计划，第 3 条（回读卡点）按"直接走共享事务 + 提取器回读"解决。

1. 新窗口「镜头效果」，拥有 `camera` + `camera:background` 两层；窗口内是**有序效果列表**（上移/下移/删除/添加），顺序即时间（§6 表格第 2 行）。
2. 写回整层：`PreviewReplaceResource(sourceText, expectedRevisionSha256, resourceKey, directives)`（§3），0 条＝删除该层。
3. **必须同时解决写回后的校验路径**：`EditorCommandDocumentService.ReadSelection`（MoreEffects/Interop）在读取时用 `_composer.Read`，它对"同一资源多条"**返回失败**；`ApplyUpsertSelectedOnMainThread` 结尾正是用它回读 After。所以镜头窗口的写入即使成功，也会在回读处报失败。需要一个以**提取器**校验的 apply/preview 路径（`WriteExact` 本身不依赖 1:1，只有回读依赖），并保持 token + revision 双重核对不变。
4. 时间轴删除后，`docs/42` §3、§6.1、§6.2 与 `docs/43` 里的面板部分成为历史记录，不再是当前实现。
