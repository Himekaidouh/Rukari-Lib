# Android / PE 静态比对（2026-10-14）

用户报告 PE（Android）版 AA 在**点开 Script 节点的一瞬间闪退**，此前没有任何崩溃日志或堆栈。本文记录在**不接手机**的前提下能取得的全部静态证据：把 PE 包与 PC 包的 IL2CPP 声明面逐项对照，看闪退能否由"成员缺失 / 签名不符 / 类型被 strip"解释。结论与下一步见文末。

**只读声明与文件元数据**（类型、成员名、字段偏移、方法 RVA/Offset），不读取、不打印、不复制 AA 官方方法实现；遵守 [Android/PE 适配交接](27_Android_PE端适配交接_20261006.md) §7 的规则。

## 1. 结论（先说结果）

| 检查 | 结果 |
| --- | --- |
| 我们 Harmony patch 的 23 个目标方法 | **签名逐项一致，且 PE 上都有真实代码地址（RVA 非 0）** |
| 例外 | 只有 `UIInputOnGUI.OnGUI` 在 PE 上不存在（整个 `UIInputOnGUI` 组件被 strip）。我们的 `ToolInputService` 对"任一键盘目标缺失"已有降级：整组卸载并关闭工具搜索框，不崩（`src/Rukari.Lib.Runtime/Tools/ToolInputService.cs` 第 66–86 行） |
| 我们直接读的游戏字段 / 属性 | 名称全部存在，**字段偏移逐项相同**（如 `scriptNodeListItemsCache` 0xE8、`LocalOverrideData` 0xA0、`BodyColor` 0x70、`autoDelayInSeconds` 0x90、`previewMode` 0x139、`currTask` 0x30） |
| 我们 DLL 引用的 Assembly-CSharp 成员 | **292 项全部可解析**（其中 132 项是"游戏字段被 interop 暴露成属性"） |
| 外部程序集 | 我们引用的 8 个 Unity 模块与 `Assembly-CSharp` / `spine-*` / `Newtonsoft.Json` 等在 PE 上都在；PE 缺少的 6 个模块（`AIModule`、`TerrainModule`、`DirectorModule`、`MarshallingModule`、`AccessibilityModule`、`UnityAnalyticsModule`）我们**一个都没引用** |

**因此："某个成员在 PE 上不存在 / 签名不同"这一大类基本被排除。** 闪退还剩的可能是运行时与原生层面的（按优先级）：

1. **PC interop 编译产物 vs Android 运行时生成的 interop**：我们的 DLL 是对着 PC 的 `Assembly-CSharp.dll` 编译的；ARM64 上的委托封送（`SetVoice(string, Action)`）、结构体/byref、Harmony detour 都必须单独验证（docs/27 §10.1 已列为 P2 前提）。
2. **自有 MonoBehaviour 的类注册 / 注入**：工具箱与编辑器是进入 Script 工作区时才第一次创建自有 Unity 组件，时间点与"点开一瞬间"完全吻合（docs/27 §10.2）。
3. **主线程与对象寿命**：识别 Script 工作区、读 Inspector / NGUI 对象都发生在这一刻。
4. **被我们调用的官方方法内部原生崩溃**（`DataList`、`get_ScriptKr`、`UIPanel` 读取等）。

**架构事实（决定"能不能模拟"）**：AA APK 同时含 arm64-v8a / armeabi-v7a / x86 / x86_64 的 `libil2cpp.so`，但 **Launcher APK 的原生库只有 arm64-v8a**（18 个 `.so`，含 `libcoreclr.so`、`libclrjit.so`）。Mod 只能经 Launcher 装载，所以 x86 模拟器进不了这条加载链；即使用 ARM 翻译层跑起来，翻译层恰好位于要观察的 ARM64 原生边界之前，结论不能外推到手机。**PE 环境无法有意义地模拟，必须用真实 arm64 设备。**

## 3. 方法（可复现）

```text
工具：Il2CppDumper v6.7.46（net7-win，SHA256 55C8B397A0C5DCF79F4E201BD6472F3205BAF9E66F6FA510A2B9E2099AAFBAB2）
配置：DumpMethod/DumpField/DumpProperty/DumpFieldOffset/DumpMethodOffset = true，GenerateStruct = false，RequireAnyKey = false

PE：libil2cpp.so(arm64) + pe-global-metadata.dat   → CodeRegistration 0x69F22D0、MetadataRegistration 0x6CB4630，il2cpp 版本 29.1
PC：GameAssembly.dll    + PC global-metadata.dat   → CodeRegistration 0x1838757A0、MetadataRegistration 0x1840BBBC0，il2cpp 版本 29.1
产物（本地 artifacts/pe-audit-20261014/，不进仓库）：dump-pe/dump.cs 47,862,324 字节、dump-pc/dump.cs 42,439,716 字节
引用清单：用 System.Reflection.Metadata 读我们六个 DLL 的 MemberRef / TypeRef / AssemblyRef → memberrefs.tsv 844,431 字节
```

比对规则：引用按"声明类型简单名 + 成员名"匹配；由于 interop 把游戏字段暴露成属性，`get_X` / `set_X` 允许落到同类型字段 `X`；dump 文本按缩进栈处理嵌套类型归属。

### 5.2 需要抓全的证据

1. BepInEx `LogOutput.log`（本次启动完整一份，不只是最后一条警告；路径从 `BepInEx.Paths` 取，别硬编码桌面路径）。
2. `logcat -b main -b system -b crash` 的复现时间段（不清空系统日志、不只按包名过滤，因为游戏跑在 Launcher 容器里）。

**建议同时做分段诊断构建**（docs/27 §8.3）：把"宿主纯服务 / 共享编译 / 工作区可见性 / 选句读取 / 共享输入 / 面板渲染 / DataList / 播放器观察 / 实际变换 / 配音资源 / 配音播放 / 动画等待"各自开关，默认只开纯服务，一组通过再开下一组——这样手机在手上时一次会话就能二分，而不是来回换包。

## 6. 追加：手机上实际安装的稳定包（0.4.2 / 1.4.1 / 1.6.4）

用户确认出问题的手机装的仍是教程那三个稳定包，因此对**这套 DLL** 也做了一遍同样的引用比对（从教程 ZIP 解出，六个 DLL：`Rukari.Lib.dll` 4F4CA9237C8F4922、`Rukari.Lib.Runtime.dll` D7E89AF32A0C1E47、`Rukari.MoreEffects.dll`、`AzureArchive.VideoTools.Core.dll` 731DB05F56F3F769、`AzureArchive.VideoTools.Formats.dll` 87A732D38DE3278B、`Rukari.CharacterVoice.dll` 7ED715D30BBBC8F3）：

| 检查 | 稳定包（手机在用） | 当前发布版 |
| --- | --- | --- |
| 引用的 Assembly-CSharp 成员 | 246 项，**全部可解析** | 292 项，**全部可解析** |
| 其中"字段即属性" | 132 项 | 156 项 |
| 解析不到的残留 | 3 项（`CommandEntry..ctor`、`Script..ctor`、`UIInput.Set`） | 5 项（多 `ScenarioAnimation.WaitAnimation..ctor`、`UIToggle.Set`） |

残留项已逐条确认是**文本解析器的盲区**，不是真实缺口：`.ctor` 是构造函数名字正则不匹配；`UIInput.Set` / `UIToggle.Set` 在两边 dump 里都存在（`public void Set(string value, bool notify = True)`），签名级比对也报"两边一致"。另有一批形如 `UIRect.AnchorPoint`、`AdditionalPromptCommandHelp.CommandEntry`、`ScenarioUtil.ScriptInfo` 的成员是**嵌套类型**，Il2CppDumper 以带前缀的形式渲染，需要单独归位才不掉；这些名字在两份原始 metadata 里也都存在（已用原始字符串检索逐项确认）。

**因此对手机上那套包，结论与上一节完全相同：不是缺成员。**

## 7. 边界

本文全部结论来自**文件与声明**：没有连接手机、没有安装或运行 PE 包、没有取得任何崩溃日志，也没有读取官方方法实现。它证明的是"我们已知要碰的成员在 PE 上都在"，**不证明** PE 上这些调用会成功——委托封送、类注册、主线程与对象寿命都必须靠实机证据。构建、托管检查与本文的静态比对都不能替代实机验收。
