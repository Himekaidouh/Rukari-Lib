# 开发诊断接口与保存链路检查

这是一套给开发者和报错收集使用的只读诊断入口，不属于用户安装包。入口脚本是：

`src/scripts/Collect-DeveloperDiagnostics.ps1`

如果没有合适的真实工程，可以先生成隔离样本：

```powershell
pwsh -File .\scripts\Generate-IsolatedTestPair.ps1 `
  -OutputDirectory '.\artifacts\isolated-test-data\manual'
```

它会在指定目录生成独立的 `projects/<工程名>.aap` 和 `saves/<工程名>.aas`，内容由托管测试使用的合成构造器生成，包含一条普通对白和一条 AAVT 额外指令。生成目录不会写入 AA 的真实存储，也不会进入用户包；可以把这个目录作为 `-DataRoot` 传给诊断脚本。

生成器还会自动写入 `AzureArchive.VideoTools/workspaces` 下的 workspace 证明，使用内部 `#char;...` 指令验证“读取 → 映射 → 编译 → workspace 写入”链路。

## 使用方式

在仓库的 `src` 目录执行：

```powershell
pwsh -File .\scripts\Collect-DeveloperDiagnostics.ps1 `
  -GameRoot 'E:\AA1.01' `
  -DataRoot 'E:\AA1.01\AzureArchive_Data\data' `
  -ProjectName '工程名'
```

如果只想收集游戏和 BepInEx 信息，可以省略 `-DataRoot`。如果不希望运行托管测试，增加 `-SkipManagedTests`。

保存前后可以使用 `-BaselineReceipt` 做回执对比。先在点击“保存并发布”前收集一次，再保存后用第二次收集指向第一次的 `diagnostic-receipt.json`：

```powershell
pwsh -File .\scripts\Collect-DeveloperDiagnostics.ps1 `
  -GameRoot 'E:\AA1.01' `
  -DataRoot '实际的 AA 存储根目录' `
  -ProjectName '工程名' `
  -OutputDirectory '.\artifacts\diagnostics\after-save' `
  -BaselineReceipt '.\artifacts\diagnostics\before-save\diagnostic-receipt.json'
```

第二次回执的 `Comparisons` 会列出匹配文件的前后大小、时间和 SHA-256；AAP/AAS 同时具备哈希时，以内容哈希和大小判断是否变化。这样可以把“保存按钮返回”与“正式播放档案真的更新”分开验证。

脚本会把诊断回执写入 `src/artifacts/diagnostics/<时间>/`，包括：

- AA、BepInEx、Interop 和补丁器的存在性、文件大小、修改时间和 SHA-256；
- `BepInEx/LogOutput.log` 以及最近的日志尾部；
- Rukari 配置中的诊断开关；
- 指定数据根目录下的 `projects`、`saves`、AAP/AAS 文件；
- 全部 AAP/AAS 的配对完整性，以及孤立的 AAS；
- AAP、AAS、映射和 workspace 的托管检查；
- 完整托管测试套件的输出；
- `diagnostic-receipt.json` 和方便贴给开发者的 `diagnostic-summary.txt`。

脚本不会启动游戏，不会调用官方保存、编译或发布方法，不会安装或覆盖 DLL，也不会修改 `GameRoot`。输出目录位于 `artifacts` 下，打包脚本会排除它。

如果需要观察游戏内的真实保存调用，仍应在开发副本中手动打开已有的诊断开关，再重启 AA：

- 人物配音支持：`ProbeAuthoringSave`、`ProbePublish`、`ProbeAuthoringCatalog`；
- 更多的画面效果：保留现有的播放器观察和映射诊断开关；
- 运行后将对应的 `BepInEx/LogOutput.log` 与 `BepInEx/config` 一起交给诊断脚本收集。

这些开关只记录入口、参数、异常、耗时和文件结果，不应在普通用户包中默认打开。诊断脚本本身也不会替用户修改它们。

## 保存链路目前的真实边界

“工程保存”按钮仍使用官方入口，顺序固定为：

1. `StudioCommon.Save(false)`；
2. `StudioCommon.Compile()`；
3. `StudioCommon.Compile(projectName)`，生成正式播放档案。

当前按钮的三项状态表示对应官方方法没有抛出异常。它还没有在按钮返回的同一时刻重新读取并校验 AAP/AAS 的内容哈希、时间戳和映射，因此“发布完成”不等于已经证明正式播放索引可读。运行时随后会重新扫描和校验；若 AAS 写入尚未落盘、存储路径发生变化、或 AAP/AAS 不属于同一工程，正式播放仍可能失败。

因此，遇到“预览有效、正式播放无效”时，诊断顺序应是：

1. 用 `-DataRoot` 和 `-ProjectName` 检查实际 AAP/AAS 是否成对存在；
2. 检查两份文件的修改时间和 SHA-256 是否在保存后变化；
3. 查看全目录配对完整性，以及 AAP/AAS 解析、映射和 workspace 检查的失败项；
4. 再结合游戏日志判断是路径、编译发布、映射、ABI 还是运行时派发问题。

这套接口专门补齐了证据收集，暂时不改变保存逻辑。后续若要把“发布完成”升级为强确认，应在官方调用返回后加入同一工程 AAP/AAS 的重新读取、映射重建和成功条件，而不是增加一次盲目重发布。

## 建议的开发测试矩阵

对同一个工程至少分别记录以下结果：编辑器预览/正式播放、空对白/非空对白、AUTO/手动推进、首次冷启动/切场景、默认存储路径/自定义存储路径，以及只启用 Rukari 和同时启用 FL 的组合。每次只改变一个条件，并保留诊断回执，避免把“按钮没有报错”误判成“画面已经生效”。
