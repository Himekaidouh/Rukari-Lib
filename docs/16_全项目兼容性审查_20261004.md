证据分为三类：

## 2. 这轮已经改了什么

1. 保留真实第一条编译日志及其所在窗口，在原先窗口时序不合时允许延后核验，不借用旧台词的全局身份。
2. 完整证明相同、同主线程、同真实打开窗口的重复 DataList 可复用当前代，避免刷新抹掉 FIRST；场景、上下文、台词、额外指令任一变化仍开新代。
3. 已确认台词按真实播放窗口授权重播；同一个窗口去重，旧的一次性公开接口保持原签名和语义。
4. 完整授权后才更新覆盖缓存、继承状态与同帧去重信息；拒绝路径不污染下一次真正可执行的窗口。
5. LateUpdate 派发前再次检查代、窗口和身份；选句变化使旧排队任务失效。
6. 观察队列溢出时仍推进真实关闭水位，避免已关闭窗口被当成打开。

上述实现的上轮完整构建为 714 项托管检查、四示例和四插件依赖检查通过；这不是本轮新增测试，也不代表实机全通过。

### C08/C09：共享编译入口与变换合成

本项目共享指令服务的 `#aavt` 注册不占 FL 官方 FL-Move 键。本轮没有发现这两个注册键重名；**不能用“注册冲突”概括现在的重播故障。**

旧 FL 源码与 `src/Rukari.Lib.Runtime/Commands/EmbeddedDirectivePatch.cs:20-65` 会分别接触三编译入口；`ContinueDialogueRuntime.cs:69-110` 与旧 FL 也各自接触 ParseScript。共享服务仅能保证其内部注册 namespace 完成净化；独立 postfix 若随后改返回文本，捕获的 hash 未必是最终 hash。旧 FL 的旧式/新式 A 净化存在此可能；当前推荐 B 写法 `#3;FL-Move;…` 在那份源码中保留，不能据此解释本轮 C01。

建议方向是协调一个原生入口负责处理，各 Mod 通过托管服务参与，并在所有处理完成后统一确定身份。单加 Harmony 顺序不能自动消除 IL2CPP 多 detour 的兼容风险。5.2.0 要以作者源码或观测证据核对，不能反编译补证。

立绘方面，AAVT 的 CharacterTransformService/CharacterPresetRuntime 修改人物 root；旧 FL 正常写 Char_Pos 祖先，不一定是同一个对象。但 FLSlots.cs:556-557 存在 CharPos 回退 SpineRoot，rotation/scale 帧末覆写，此时可能覆盖 AAVT 同 root 变换。需要按实际 Transform 身份和轴约定独占或相对合成，不只按槽位判断。

AAVT 预设用 Stopwatch，旧 FL 用 realtimeSinceStartup；没有共同故事暂停/快进时钟契约。此项与 C01 授权失败分开。

验收：两加载顺序、FL 三种语法、三个编译入口及 ParseScript；不同槽/同槽不同轴/同轴；正常层级/回退层级；旋转、镜像、缩放与预设；换人、换卡、结束复位、暂停恢复。需要可观测的最终文本和变换对象身份，不用“没有报错”替代视觉验收。

### C12：性能与诊断归因

`src/AzureArchive.VideoTools/Runtime/PlayerCommandObservationLog.cs:65-79` 在锁内同步 File.AppendAllLines，无文件大小/历史保留上限；编译捕获与预览缓存路径也调用它。慢盘、杀软扫描或大量重复刷新可能增加开销，但本轮没有受控对照证明用户卡顿来自这里。

`PlayerCommandObservationRuntime.cs:507,516,557-560,579-611` 的 Update 计时不覆盖前置预设 Update、最后的连续对白处理、LateUpdate、Lib UI 和配音/Spine 模块。因此日志 `ours=False` 只说明测量区段未占主要间隔，**不能排除本项目其他路径，也不能直接归因官方 AA**。
