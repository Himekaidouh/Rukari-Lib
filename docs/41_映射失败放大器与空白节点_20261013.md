## 1. 用户反馈的三条

1. `#wait` 的毫秒数**小于**扩展指令的动作时长；
2. 工程里存在**没有连接的空白 script 节点**；
3. **有内容的节点没有被上下文连接**。

用户称这三条都会导致「扩展指令动作无法在播放模式里显现」。

## 2. 第 1 条：已修复（实机确认）

| --- | --- | --- |
| row 1 派发（600 ms） | 01:05:58.3204 | — |
| row 2 窗口 | 01:05:58.9357 | **+615 ms** |
| row 2 派发（600 ms） | 01:05:58.9474 | — |

修复前是 5.2 ms / 3.8 ms，且 `action-timeline` 只有 `parse failed`、没有 `armed`。现在 `armed`/`released; status=Completed` 各 3 次、0 超时。见 `docs/40_动作保持门修复_20261013.md`。

## 3. 第 2 条：空白节点确实会造成损伤，但形态不是「完全不显现」

用户 01:13–01:14 亲自复现（在 `测试-修复1` 里拖入一个空白 Script 节点 `0fb03f21-…`，`Scripts: []`，连通）：

| 时刻 | 事实 |
| --- | --- |
| 01:14:06（加节点前） | `records=4; batches=2`，row 1/2 派发正常 |
| 01:14:33（加节点后） | `aasRecordsScanned=`**6**`; records=`**6**，row 1/2 仍正常 |
| 01:14:35 | **新增** `sequence=19; status=FAIL_CLOSED; reason=conflicting-embedded-command-captures` |

即：空白节点让官方编译器多产出 **2 条 AAS 记录**，并让**某一行**变成「同一推进窗口里出现两个不同命令批次」→ 该行整行 fail-closed。用户当时盯着的那两行恰好没被选中，所以主观感受是「似乎没有问题」。

离线复现台（`artifacts\blank-node-repro\`，只动副本）结论：

| 变体 | sourceScenes | ambiguous | unmapped | 仲裁 |
| --- | --- | --- | --- | --- |
| baseline | 4 | 0 | 0 | PASS |
| 空节点、0 行 | 4 | 0 | 0 | PASS |
| 空节点、1 空白行（未连接） | 5 | 0 | 1 | PASS |
| 空节点、1 空白行（连接） | 5 | 0 | 1 | PASS |
| **未连接但有内容的节点**（整节点复制） | 8 | **4** | 4 | PASS |

所以：**孤立空节点本身不会改变仲裁候选集**（候选只来自 AAS 记录），也不会平移其它节点的锚定 offset（offset 按节点分组）。它只能通过「让官方编译器多产记录」间接起作用。

## 4. 真正的放大器：一行无法映射 ⇒ 整档失败

```csharp
// CommandTimelineCompiler.cs:315-324
if (!mappings.TryGetValue(location, out ScenePlaybackMapping? sceneMapping)
    || sceneMapping.Status is not (UniqueDialogueTextMatch or AnchoredNodeSequenceMatch
        or ObservedCompilerRecordMatch)
    || !sceneMapping.PlaybackRecordIndex.HasValue)
    return Fail($"Enabled commands at scene {location} require a unique playback mapping.");
```

只要有**任意一行**带启用命令却拿不到唯一记录，**整个工程的嵌入式投影编译直接失败**：

```
index-load status=PENDING; reason=publish-pending;
  diagnostic=reason=embedded-projection-compile-failed; … Enabled commands at scene
  49a2c00f-a3ed-4e56-962c-bd0ba0521026:1 require a unique playback mapping.
→ 播放期所有窗口 status=NO_INDEX → 一条命令都不出现
```

实证：`player-command-observation-20261013-002140.log:1101 → :1120`、`player-command-observation-20261012-090514.log:381 → :403`（AAS 重建后 0.6 秒恢复）。这才是「完全不显现」的最强解释，也正是用户反馈第 2、3 条对应的机制。

**好消息**：这条错误**本来就点名了出问题的场景**（`scene <nodeGuid>:<index>`）。因此下一个用户反馈只凭日志就能指到具体哪一行，不需要对方的工程文件。

放大器的触发前提是「某行拿不到唯一映射」，而空白行/多余记录正是通过它起作用的：空文本行被排除在文本匹配之外，只能靠**同节点锚定序列**落位，而锚定序列要求**该节点每一行都与 AAS 记录逐行对齐**（`ProjectPlaybackMapping.cs:244-263`）；官方编译器在这个节点的行区间里多出记录时，整段锚定作废 → 该行 `Unmapped` → 放大器点火。

## 5. 为什么不改放大器（已试过并撤回）

把「整档 Fail」改成「丢掉该行 + 点名告警」的改动**红了 7 个既有测试**：

```
CapturedEvidenceRejectsArchiveRevisionsLengthsAndSchemaDrift
CapturedEvidenceRejectsDuplicateSourcesAndRecords
CapturedEvidenceRejectsSceneRecordAndIdentityContentDrift
MappingSidecarRejectsModifiedProjectOrPlaybackContents
MappingSidecarMalformedJsonAndNullEntriesRemainFailClosed
NativeFormatAdaptationDoesNotInventEmptySceneCompilerProof
RoundTripsTimelineAndProjectionWithAtomicBackups
```

这 7 个钉住的是同一条**数据完整性规则**：映射证据漂移、被篡改、JSON 损坏或缺证据时，必须整体拒绝，不得据此派发。放宽放大器会把「证据不可信」也变成「丢几行照常跑」，属于**悄悄削弱已测试的保证**，因此撤回（`CommandTimelineCompiler.cs` / `CommandTimelineContracts.cs` / `EmbeddedProjectCommandCompiler.cs` / `PlayerCommandObservationRuntime.cs` 全部复原，撤回后 646/0 全绿）。

## 6. 已确认的处理方向

**修根因，不动放大器**：放宽锚定提议 —— 由同节点内唯一匹配行确定唯一 offset 后，**只校验目标记录自身**，不再要求整节点逐行对齐；空文本行仍按现有安全规则需要同节点唯一 offset 支撑。这样映射恢复正常，放大器不再有点火机会，且不触碰任何完整性规则。

保留不动的 fail-closed 规则：身份+行号判定、跨 pair 歧义拒绝、一条记录被两个命令场景占用即失败、证据被拒（`CompilerMappingEvidenceRejected`）必须失败。

## 7. 给下一次用户反馈的诊断配方

只看两个签名即可分流：

| 日志签名 | 含义 | 下一步 |
| --- | --- | --- |
| `index-load status=PENDING … require a unique playback mapping` + 大量 `status=NO_INDEX` | 一行映射不唯一，**整档**被拒 | 看同一行点名的 `scene <guid>:<index>`，让作者检查该行所在节点是否有多余/空白行或孤立节点 |
| `auto-discover … status=AmbiguousPlaybackScript` + `NO_INDEX` | 同身份多条记录且缺行号，配对未建立 | 看是否有多行编译成同一脚本（空对白行常见），检查 AAS 是否与 AAP 同版本 |
| `auto-discover status=READY` 但无 `SCENE_COMMAND_DISPATCHED` | 配对正常，问题在派发/映射细节 | 看该行 `observation status=…` 的具体状态与 `conflicting-embedded-command-captures` |

## 9. 第六个放大器：指令 token 拼错（2026-10-13 发现）

`#aavt;camera;…` 的 `scope=` 只接受 `overall` / `background`，其它拼写**不是静默忽略而是直接 Fail**（`SceneCameraDirectiveParser.cs:142-147`）。该错误经提取器变成 `reason=embedded-command-invalid` ⇒ **整档索引加载失败** ⇒ 播放期全部 `NO_INDEX` ⇒ 作者看到「整个工程播放里一条命令都没有」。

报错串会点名出错的 token，所以可诊断；但它与 §4（映射不唯一）、§9.2 的两条（编译期重复槽位、作者入口重复槽位）同属「一处小错 → 全工程静默」的形态。同一形态的其它入口也应一并收口，方向与 §6 一致：**局部错误只废掉那一处，不要废掉整档**。

### 10.1 已实施（2026-10-13）：失败串带上作者可读的定位

用户选择「只改诊断，不动行为」。`EmbeddedProjectCommandCompiler.cs` 的失败串现在多两个字段：

```text
reason=embedded-command-invalid; node=<节点名>; scene=<guid>:<index>; dialogue=<该行台词片段>; Line <n>: <原因>
```

`node=` / `dialogue=` 经新增的 `Locator()` 折叠控制字符并截断（24 / 32 字符），保证一条失败只占一行、不会把日志冲散。夹具 `EmbeddedDiagnosticsTests.InvalidEmbeddedSceneErrorCarriesStableReason` 扩展两条断言（`node=Main;`、`dialogue=A;`），总数仍 678/0。

### 10.2 为什么"出错行原文"没有进去

`EmbeddedDiagnosticsTests` 有一条**刻意**的断言：这个失败串里不得出现作者原文（`AssertEx.False(result.Error.Contains("camera;set"))`）。原因是该串会跟着编译证据走，而 embedded-only 契约要求作者的 `additionalPrompt` 原文不进证据。所以定位靠「节点 + 台词行 + 行号 + 报错点名的 token」，不靠回显原文。

若确实要看原文，正确做法是**只往诊断日志**加一条独立的 author-facing 行（不进入 `Error`），需要把出错行从提取器单独带出来——属下一步，不与本轮改动混在一起。
